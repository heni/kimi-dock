# Дизайн: переукладка тулинга чатов — capability из привязки чат↔директория

Дата: 2026-11-28. Статус: **предложение к утверждению владельцем**.
Основание: серия 3.9.x (3.9.0–3.9.4) — пять заплаток на одну
структурную кривизну; репорт владельца 2026-11-28 (новый чат, просьба
«создай заглушку проекта» — модель отвечала «доступа к файловой
системе нет»; владелец создал первый файл руками). Анализ опирается на внутреннюю критику архитектуры и модель
пользовательских ожиданий (выводы distilled в §1–§3) и на обзор 14
конкурирующих систем (источники в §7). При утверждении владельцем
заменяет прежний дизайн тулинга целиком: там, где этот текст ему
противоречит, верен этот; единственное подтверждённое там решение,
которое этот текст сохраняет: помощь живёт в чате самого артефакта,
выделенный диалогностический чат отклонён.

## 1. Проблема

Способность модели работать с файлами сегодня — производное от
истории сообщений, а не свойство продукта:

- Инструменты цепляются к сообщению-маркеру `Message.runHelp`
  (ставит только ✨); побеждает последний маркер; липкость —
  производная. Пользователь не видит ни состояния, ни границы:
  обычное «исправь файл» в немаркированном чате идёт к модели без
  рук, а после одного ✨ руки тихо появляются у всех следующих
  сообщений.
- Правила способности размазаны: gating кнопки (renderer), валидация
  payload (main), текст скилла, деградации, e2e-ограничения. Ни одно
  место не отвечает на вопрос «что может ИИ в этом чате».
- Один инвариант — «несохранённая работа пользователя не затирается
  молча» — реализован четырьмя отдельными механизмами (отказ записи
  по снапшоту буферов, баннер ревалидации, save-time guard, skip
  save-all), потому что истина о файлах живёт в renderer, а main видит
  лишь per-pass снапшот.
- Два скилла (run-help и run.json) с двумя разными моделями арминга
  (per-conversation перманентный vs глобальный session-only) и
  пересекающимся содержимым; run.json-арминг — пережиток 3.5.0.
- ✨ ради показа ответа мутирует persisted-настройку `forceOfflineMode`
  — view-роутинг через отладочный флаг.
- Ассоциация чат↔директория — неявная (соглашение об имени, ленивое
  создание); каждый потребитель (пикер, триггер, деградации)
  пере-выводит её сам.

Каждая заплатка 3.9.x локально правильна; вместе они означают, что
определения не существует ни в одном месте.

## 2. Принципы (консенсус поля, §7)

Обзор 14 систем (терминальные агенты, IDE, чат-продукты, async-агенты)
даёт повторяющиеся решения, независимо повторённые ≥3 раз:

- **P1. Привязка workspace — это и есть грант.** Открытый каталог /
  репозиторий / аплоад определяет, что агент может трогать; граница
  видна всегда (status bar / working set). Никто не прячет привязку.
- **P2. Один фиксированный постур автономии, без режимов.** Лестница
  консенсуса: чтение в workspace — всегда; запись в workspace — после
  хода, инициированного пользователем; всё вне — никогда (не диалог
  подтверждения, а предложение attach-read-only / copy-in). Режимная
  пролиферация (Roo, ранний Windsurf) рынком пройдена и отвергнута:
  выжившие имеют 2–3 ступени, не больше.
- **P3. Undo — примитив, делающий автономию приемлемой.** Snapshots /
  checkpoints + one-click restore; «откат в один клик», а не «доверься
  модели».
- **P4. Tool-calls — компактные блоки в транскрипте; ревью после, на
  диффах**, а не до, на попапах.
- **P5. Память — в файлах-правилах (rules-as-code)**, перечитываемых
  каждый запрос; разговорные инструкции не переживают компактификацию.
- **P6. Диск — сессия.** Для стейтлес-API это достижимо тривиально:
  файлы живут в user-owned директории, транскрипт лишь ссылается на
  пути. Анти-паттерн (session-bound sandbox, файлы умирают с сессией)
  структурно невозможен.

## 3. Целевая архитектура

### 3.1 Capability — свойство чата, не сообщения

Правило одного места: **offline-разговор имеет инструменты на свою
chat-директорию** (`resolveChatDir(conversation.id)`), директория
создаётся по требованию. Никаких маркеров, липкости, last-wins,
toolsChatId-расщепления, деградаций.

- ✨ остаётся только как предзаполнение вопроса (диагностика запуска /
  бутстрап первого артефакта): меняет текст сообщения, не способность.
  Цепочка `App.runHelpTrigger` (prop + consume-once + ref-гарда)
  упрощается до обычного вызова.
- Вопрос «про артефакты чата A в свежем чате B» (Alt+click) — в чат
  самого артефакта (подтверждённое ранее решение, здесь сохранено).
  Если когда-нибудь понадобится межчатовая постановка — одно явное
  поле ассоциации, видимое в шапке, а не маркеры в истории.

### 3.2 Системное сообщение: тонкий always-on + ленивый скилл

Сегодняшний монолитный SKILL.md дублирует инструменты прозой поверх
структурированных схем, инлайнит схему run.json и отсутствует на
обычных проходах — анти-паттерн «one giant always-on rules blob» (§7).
Раскладка по принципу «упомянут всегда, загружен по необходимости»:

- **Always-on (5–7 строк, каждый offline pass):** identity и границы
  («ты — ассистент в Kimi Dock; есть инструменты над директорией этого
  чата; за пределы не выходишь, программы не запускаешь») + одно
  правило-приглашение: «когда пользователь просит операцию с файлами —
  сначала вызови tooling_rules()». Закрывает репортченный кейс: модель
  знает границу по построению и называет её, а не выдумывает отказ про
  чужие продукты.
- **Ленивый скилл (`tooling_rules()`):** документ с рецептами
  (freshness-контракт в сжатом виде, схема run.json, answer contract,
  empty-dir случай) модель загружает вызовом ровно при явном намерении
  пользователя выполнить операцию с файлами. Токены экономятся на
  каждом разговорном проходе; сам факт загрузки — видимое событие в
  транскрипте (усиливает §3.4); контракт читается непосредственно перед
  действием. Иного канала принуждения для freshness нет — harness
  защищает файлы, актуальность чтений — за моделью.
- **Схемы инструментов — единственный источник правды.** Прозаические
  описания пяти инструментов из скилла удаляются; safety-флор (отказ
  при несохранённом буфере, confinement) живёт в description схем —
  они всегда в контексте, ленивому доку он не нужен.

Удаляются: `runSkillArmed`, чип в шапке, кнопка «AI: run.json» и
глобальная утечка инструкций во все чаты; прозаические дубли
инструментов; always-on блоб.

### 3.3 Видимость вместо армингов

Шапка offline-чата показывает: название чата; состояние директории
(«📁 3 файла» / «📁 пусто» / «папки ещё нет — создастся первой
записью»); capability-строку («инструменты: директория этого чата» /
«задайте workspace-папку в настройках»). Кнопка 📁 Artifacts всегда.
Два визуально одинаковых чата с разной способностью невозможны по
построению.

### 3.4 Транскрипт говорит о фактах

Каждый tool-call — компактная сворачиваемая строка («read src/main.rs»
/ «created Cargo.toml»); каждая запись — факт-строка с действием
«открыть в редакторе»; per-turn сводка touched-files. Машинный
триггер ✨ рендерится действием, а не чужой репликой в истории.

### 3.5 Undo: snapshot на ход

В начале хода, инициированного пользователем, — дешёвый snapshot
изменённых файлов директории; «откатить ход» в один клик + просмотр
диффа хода. Существующие защиты от внешних правок (save-time guard,
баннер) остаются — это вторая половина той же истории (диск делят двое).

### 3.6 Истина о файлах — в main (глубокий фикс, отдельный юнит)

Реестр драфтов и версий в main вместо per-pass снапшотов: отказ записи
по живому состоянию; save/save-all по версиям; четыре защиты
несохранённой работы схлопываются в одну. `lastRunByChat` персистится
рядом с историей команд панели. Не начинается, пока не закрыты §3.1–3.5
— это единственная часть с новой машинерией.

### 3.7 Контекст

- **Правила**: `rules.md` в корне chat-dir (обычный артефакт — модель
  читает/пишет его прозрачно; глобальный файл — backlog). Правило
  «ссылаться, не инлайнить».
- **Манифест**: возвращается `read(path)` по директории (§3.8);
  repo-map с ранжированием — анти-паттерн для директорий этого масштаба.

### 3.8 Инструменты: состав и принцип

Принцип (решение владельца 2026-11-28): инструментов меньше, каждый
универсальнее — но универсальность ограничена, ибо обобщение — источник
ошибок модели и уязвимостей. Универсальность допустима там, где
обобщается сама концепция (чтение «чего угодно по пути»), и
недопустима там, где пришлось бы вводить полиморфное намерение (один
аргумент — разные виды работ по ключевому слову: такие инструменты
модель путает, а их схемы нельзя проверять строго).

Целевой состав — четыре:

- `read(path)` — единое чтение: файл (content + header: источник,
  размер, mtime) или директория (манифест: пути+размер+mtime+флаги
  несохранённых буферов). `run.json` и `rules.md` — просто пути.
  Слияние нынешних `read_artifact` + `list_artifacts` + `get_run_json`
  (пять инструментов → три).
- `write(path, content)` — полная перезапись/создание; отказ при
  несохранённом буфере и confinement живут в description схемы.
- `get_run_output` — состояние run-сессии main, не файловая система.
  Намеренно НЕ сливается с `read`: виртуальные пути в файловом
  namespace — ровно тот источник ошибок, который принцип запрещает.
- `tooling_rules()` — ленивая загрузка скилла (§3.2); действует над
  контекстом, не над миром; в транскрипте — видимое событие.

Сознательно не даём (именованные backlog-кандидаты, не v1):

- **Shell (`run_file`)** — консенсус поля даёт агенту shell с
  sandbox+аппрувал; у нас run-консоль одна и пользовательская, bash в
  директории — произвольные команды. Условие добавления: после T2,
  семантика «просьба в ходе = апрув», очередь за пользовательскими
  запусками, вывод в run panel и транскрипт.
- **WebFetch** — первая дыра границы «только директория чата»;
  fetched-контент обязан маркироваться как не-доверенные данные; капы
  и текст-экстракция — своя машинерия. Условие: реальная повторяющаяся
  потребность, отдельный маленький юнит.

## 4. Что удаляется

`Message.runHelp` и его обработка (runHelpPassInfo, last-marker-wins,
adoption-ветка); consume-once prop-триггер и ref-гарда; деградация
RUN_HELP_CHAT_DIR_MISSING (мёртва с 3.9.4); run.json-арминг целиком;
мутация `forceOfflineMode` из ✨; дублирование капов буферов (после
§3.7). Миграция данных не нужна: старые маркеры перестают читаться —
no-op.

## 5. Фазы (юниты)

- **T1 — Удаления и видимость** (3.10.0): §3.1–§3.4 + rules.md из
  §3.8 и раскладка системного сообщения из §3.2. Способность из
  разговора, один скилл, view-роутинг без мутации настроек, identity,
  шапка. Максимум кода уходит, тесты переписываются на новое правило.
- **T2 — Транскрипт и undo** (3.11.0): §3.5–§3.6 + манифест
  list_artifacts из §3.8. Факт-строки, компактные tool-блоки,
  snapshots+restore.
- **T3 — Истина о файлах** (3.12.0): §3.7. Реестр драфтов/версий в
  main; схлопывание защит. Только после приёмки T1/T2.
- **Не строится** (консенсус «нет», §7): режимы/пермиссион-страницы,
  per-tool арминг-чекбоксы сверх одного постура, MCP, OS-sandbox,
  repo-map, мульти-агентность, async/cloud, классификатор-оракул.

## 6. Честные границы (часть контракта)

ИИ не запускает программы (Run panel — пользователя, говорит об этом);
записи confined в директорию чата и c капами; отказ записи при
несохранённых изменениях цели остаётся; webview-чат kimi.ai — место без
локального доступа к файлам, и обозначен как таковой.
