# Дизайн: тулинг чатов — capability из привязки чат↔директория

Дата: 2026-11-28. Статус: **предложение к утверждению владельцем**.
Назначение: спецификация ИИ-инструментов offline-чатов. Устройство
системы — в §1–§8; обоснования, рассмотренные альтернативы и принятые
ограничения — в приложениях (§A–§C).

## 1. Пользовательский контракт

- **У каждого offline-чата есть «руки».** ИИ в чате всегда видит
  директорию этого чата и может, по просьбе пользователя, менять её.
  Никаких кнопок включения, маркеров и скрытых состояний способности.
- **Чат владеет директорией.** «Этот проект» в сообщении — это
  `<workspace>/<id чата>/`; директория появляется при первой записи.
  Состояние привязки видимо в шапке чата: «📁 N файлов» / «📁 пусто» /
  «папки ещё нет — создастся первой записью».
- **«Создай X» создаёт X.** ИИ действует, а не печатает команды для
  пользователя; если чего-то не может (вне директории, запуск
  программ) — называет реальную границу.
- **Каждое действие ИИ — факт в разговоре.** Чтения и записи видны
  компактными строками в транскрипте; запись даёт действие «открыть в
  редакторе».
- **Ход можно откатить.** Ход = сообщение пользователя + весь ответ
  ИИ. Перед изменениями файлов ИИ делает снапшот; «откатить ход» — в
  один клик, с просмотром диффа.
- **Работа пользователя не затирается молча.** Запись в файл с
  несохранёнными правками отказывается и просит сохранить; внешние
  изменения диска спрашивают, а не перезаписываются.
- **Webview-чат kimi.ai — без локальных файлов**, и обозначен как
  таковой.

## 2. Системные концепты

- **Conversation (offline-чат)** — запись разговора: id, заголовок,
  сообщения. Есть у каждого чата; по id выводится его директория.
- **Chat directory** — `<workspaceRoot>/<conversation.id>/`, дом
  артефактов чата; создаётся лениво, первой записью. Артефакты —
  не-скрытые файлы внутри.
- **Capability** — способность разговора: инструменты над своей chat
  directory. Не хранится и не настраивается; выводится: offline-чат ⇒
  есть инструменты.
- **Turn (ход)** — сообщение пользователя и весь ответ ИИ до
  завершения. Единица привилегии (записи — только в ходе, начатом
  пользователем) и единица undo.
- **Tool call** — структурированный вызов инструмента с результатом;
  рендерится в транскрипте как факт-строка.
- **Snapshot** — записанное перед изменениями состояние затронутых
  файлов; материал отката хода.
- **Hidden artifacts (dot-entries)** — служебный класс файлов: `.`-префикс,
  исключаются из панели артефактов и манифеста шлюзом; адресуются
  только по имени — моделью (system prompt называет файл), пользователем
  (явные аффорденсы UI). Сюда входят конфиг для ИИ и служебные папки.
- **Rules file** — `.rules.md` в корне chat directory: инструкции
  пользователя/проекта; скрытый артефакт; владелец — пользователь
  (редактирование через аффорденс в шапке чата), модель читает и пишет
  только по просьбе.
- **Skill (ленивый)** — документ рецептов, который модель загружает
  вызовом `tooling_rules()` при явной просьбе работать с файлами.
- **System message (always-on)** — короткий слой идентичности и границ,
  ставится каждый запрос.

## 3. Сущности программы и владение состоянием

Процессы: **renderer** (чат, редактор, UI), **main** (шлюз ФС,
исполнение инструментов, реестры), **preload** (IPC-граница).

| Сущность | Хранение | Владелец | Жизненный цикл |
|---|---|---|---|
| Conversation record | IndexedDB | renderer (`offlineManager`) | персистентен; сообщения добавляются очередью отправки |
| Chat directory | ФС под workspace root | main (шлюз) | лениво, первая записью; живёт пока нужен пользователю |
| Draft (несохранённый буфер) | реестр в main | main | session-only; write-through на каждый символ |
| Run journal | main (журнал запусков + история команд панели) | main | персистентен |
| Tool schemas | константы main (модуль схем инструментов) | main | код |
| Skill document | ресурс приложения (markdown), отдаётся через `tooling_rules()` | main | код; правки релизом |
| System message layer | константа renderer, ставится при сборке запроса | renderer | код |
| Transcript (сообщения + факт-строки тулов) | внутри Conversation record | renderer | персистентен; факт-строки не редактируются |
| Snapshots (undo) | `.snapshots/` рядом с chat directory | main | по ходу; кольцо с капом |
| Rules file | chat directory (`.rules.md`) | пользователь (правка через шапку чата); чтение — main для системного слоя | персистентен |
| Settings | `settings.json` | main | персистентен; ✨ его не меняет |

Таблица описывает целевое состояние; переход к нему — в фазах (§7).

IPC-граница: renderer шлёт запросы (`fs-*`, stream-start с телом);
main валидирует, исполняет, стримит дельты и события (в т.ч.
«артефакт записан» для реконсиляции редактора). За пределами main
модель ничего не исполняет.

## 4. Инструменты

Принцип состава: инструментов мало, каждый — одна концепция;
универсальность допустима, где обобщается само понятие, и недопустима,
где понадобилось бы полиморфное намерение (один аргумент — разные
виды работ по ключевому слову: модель такое путает, схемы не
проверить строго). Четыре инструмента:

- `read(path)` — единое чтение. Файл: content + header (источник:
  диск или несохранённый буфер; размер; mtime). Директория: манифест
  (пути+размер+mtime+флаги несохранённых буферов). `run.json` и
  `.rules.md` — просто пути.
- `write(path, content)` — полная перезапись/создание. Отказ при
  несохранённом буфере цели и confinement внутри chat directory —
  в description схемы (схемы — единственный источник правды об
  инструментах).
- `get_run_output` — последний запуск из run-журнала main (команда,
  источник, exit, хвосты stdout/stderr). Не сливается с `read`:
  это не файловая система.
- `tooling_rules()` — ленивая загрузка скилла (§5); действует над
  контекстом, не над миром; в транскрипте — видимое событие.

Намеренно отсутствуют: shell (программы запускает пользователь из Run
panel), сетевые выборки. Условия возможного добавления — §A.4.

## 5. Системные промпты и скиллы

- **Always-on (каждый offline-запрос, 5–7 строк):** «Ты — ассистент в
  Kimi Dock. У тебя есть инструменты над директорией этого чата; её
  может ещё не быть — создай записью. За пределы директории не
  выходишь; программы не запускаешь — запуском управляет пользователь
  из Run panel. Если пользователь просит операцию с файлами — сначала
  вызови tooling_rules(). Отказы называй реальную границу.»
- **`tooling_rules()` (лениво, при явной просьбе работы с файлами):**
  freshness-контракт (перечитывай в текущем ходу; числа — из header'а
  read; не заявляй о непрочитанном), компактная схема run.json, answer
  contract (причина первой, минимальный фикс, язык пользователя),
  empty-dir случай. Загружается одним вызовом, читается непосредственно
  перед действием; в транскрипте виден факт загрузки.
- **Rules file (`.rules.md`)** — скрытый артефакт (§2): main добавляет
  его содержимое к системному слою при наличии; модель читает по имени
  (листинги его не показывают) и пишет только по просьбе пользователя.

## 6. Поверхности и видимость

- **Шапка offline-чата:** заголовок; состояние директории; строка
  capability («инструменты: директория этого чата» / при незаданном
  workspace — честное «задайте workspace-папку»); кнопка 📁 Artifacts
  всегда; аффорденс «правила» — открывает `.rules.md` в редакторе
  (скрытый файл иначе недостижим для пользователя).
- **Транскрипт:** tool-call'ы — компактные сворачиваемые строки
  (включая чтения: доверие включает знание о том, что ИИ смотрел);
  запись — факт-строка с «открыть в редакторе»; per-turn сводка
  touched-files; действие ✨ — предзаполнение вопроса, а не реплика
  пользователя.
- **Редактор:** та же реконсиляция, что и для внешних изменений —
  чистый буфер перезагружается, расходящийся драфт спрашивает
  (баннер / save-диалог).
- **Undo:** в транскрипте хода — «откатить» + дифф затронутых файлов.

## 7. Фазы внедрения

- **T1 (3.10.0) — ядро:** capability из разговора; консолидация
  инструментов до четырёх; always-on + ленивый скилл; `.rules.md`; шапка
  и видимость; ✨ как чистое предзаполнение; отказ от мутации
  настроек при показе offline-чата.
- **T2 (3.11.0) — транскрипт и undo:** факт-строки и compact-блоки;
  snapshots + restore; открытые вопросы §C закрыты.
- **T3 (3.12.0) — истина о файлах:** реестр драфтов/версий в main;
  схлопывание защит несохранённой работы в одну; персист run-журнала.
- **Не строится:** режимы и permission-страницы; per-tool арминги;
  MCP; OS-sandbox; repo-map; staging-слой; мульти-агентность;
  async/cloud; классификатор-разрешений. Обоснования — §A.3.

## 8. Границы и гарантии

Записи confined в chat directory и с капами размера; отказ записи при
несохранённых правках цели; внешние изменения диска не перезаписываются
молча; undo не отменяет правок пользователя, сделанных после записи ИИ
(§C.1); webview-чат kimi.ai вне этой модели.

## Приложение A. Обоснования и история

**A.1. Почему переделка.** История 3.9.0–3.9.4: способность держалась
на маркере в сообщениях (ставил только ✨, липкий, last-wins) — видимой
модели не было; скиллы дублировали схемы инструментов; ✨ мутировал
persisted-настройку ради смены поверхности; один инвариант «не
затирать несохранённое» был размазан по четырём механизмам. Каждая
заплатка локально правильна; определения не было ни в одном месте.
Отсюда правило дизайна: способность и привязка выводятся, а не
хранятся там, где дёшево.

**A.2. Принципы-консенсус поля** (обзор 14 систем; источники §B):
привязка workspace — это и есть грант; один фиксированный постур без
режимов; undo — примитив, делающий автономию приемлемой; ревью после
на диффах, а не до на попапах; память в файлах-правилах; диск —
сессия.

**A.3. Пространство решений** (генеративный проход, 6 позиций):
advisor-in-chat (модель слепа — репорт владельца 2026-11-28 именно
этот опыт); direct-tools (выбрано; harness у нас готов с 3.7.0,
охранные механизмы 3.9.x); proposal-gated/PR (ломается у
соло-пользователя без культуры ревью); staging+promotion (граница
хороша, но у соло деградирует в слепое «accept all» и добавляет
вторую правду о файлах); виртуальная FS (машинерия reconciliation
не по бюджету); harness-intents (принято как стиль схем). Отсюда
позиция: post-land ревью + undo сильнее pre-land стейджинга для
соло-разработчика (доктрина Cline: «checkpoints make auto-approve
practical»).

**A.4. Принятые ограничения (решения владельца 2026-11-28).**
Инструментов меньше и универсальнее, но без полиморфного намерения —
обобщение источник ошибок и уязвимостей. Скилл упомянут всегда,
загружается только по явному намерению. Привязка — conversation-scoped
(chat владеет директорией): хост — чат, а не IDE; workspace-scoped
рассмотрен и отклонён. Shell (`run_file`) и WebFetch не даём: кандидаты
в backlog с условиями. Для shell: после T2, семантика «просьба в ходе =
апрув», очередь за пользовательскими запусками, вывод в run panel и
транскрипт. Для fetch: добавляется только при реальной повторяющейся
потребности, отдельным малым юнитом; при добавлении — read-only, капы и
текст-экстракция, fetched-контент маркируется как не-доверенные данные.
- **Скрытый класс артефактов (`.rules.md`, `.snapshots/`)** — введён
  решением владельца 2026-11-28: конфиг для ИИ и служебные папки не
  засоряют панель/манифест; редактирование `.rules.md` — через аффорденс
  в шапке чата. Видимая конвенция поля (CLAUDE.md/AGENTS.md) рассмотрена
  и отклонена для per-chat панели; ревизия — если пользователи станут
  искать правила глазами в панели.

## Приложение C. Открытые вопросы к владельцу (решить до T2)

1. **Undo при интерливинге:** пользователь поправил файл после записи
   ИИ — откат предупреждает и щадит его правки, или трёхсторонний
   merge? Рекомендация: предупредить + откатить только не-тронутые
   пользователем куски.
2. **Видимость чтений:** все read-строки в транскрипте или свёрнуто в
   «посмотрел N файлов» с разворачиванием? Хранить ли отдельный журнал
   «что ИИ смотрел»?
3. **Standing permission:** бывает ли «правки под src/ без
   undo-подтверждения»; если да — как показываем и отзываем scope.
4. **rules (.rules.md):** нужен ли глобальный (user-level) файл правил помимо
   per-chat?
5. **Журнал изменений:** нужен ли экспортируемый (attribution
   ИИ-правок для коммитов) или внутреннего undo-журнала достаточно?
